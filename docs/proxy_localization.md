# 少量覆盖的进程内定位验证

用户于 2026-10-18 要求同时覆盖计算与通信类定位，并在确认所有 GPU 均驻有跨节点 vLLM 后选择继续使用进程内代理。真实物理限频/背景拥塞不属于本轮范围；不把此代理测试称为论文原注入复现。

论文 3.4.4 明确提到两类故障，但图 3-7/3-8 的信号验证使用 GPU 限频；图 3-9 只按故障强度和 FLASH/GreyHound 展示 Precision/Recall，没有分别报告通信类结果或两类样本的汇总比例。正文未给出背景流量工具、速率、目标接口、持续时间及单 rank 归因方法，不能据图推断通信类独立准确率。

本轮九轮各一次，原始定义见 `results/loc-r1-matrix.json`：正常、单次 800ms 瞬态、三档计算晚到（14/126/238ms，中档目标 rank9）、三档跨节点 AllReduce 执行等待（1.75/15.75/29.75ms/调用，目标 rank0 的 size2 expert-DP 组）、一轮 EP4/TP2/PP2 计算晚到（200ms）。其余使用 EP8/TP1/PP1；16 ranks、150 步、零基 step45 注入。

随后按用户要求追加四轮位置检查：第二节点 rank9 通信中档一次（此后停止通信测试），以及计算中档 rank3、rank10、rank15 各一次。总计13轮：2个负控、7个计算代理（含混合并行）、4个通信代理。计算目标覆盖两个节点的5个不同rank。通信输出区分注入控制点、受影响rank对/通信组与唯一端点，组级命中与端点级命中分列；不能把群体传播影响直接作为多根因真值。

固定 250ms 等待为检测与20秒采样提供足够运行时间，不能用这些轮次评估训练吞吐或 FLASH 开销。所谓弱/中/强只标识注入参数；报告给出实测时延增幅与吞吐下降，不把计划档位写成实际故障强度。

计算代理在自身 rank 的计算入队前等待，检验迟到的同步信号。通信代理将等待排入自身 NCCL stream，位于探针 CUDA Event 计时区间中，不发额外背景流量、不复现带宽争用、丢包、NIC 队列或拥塞控制。因集合通信对端可能同时测得等待，即使通信组变慢，也可能无法根据最小时延唯一识别端点；这是本轮要检验的边界，而不是通过调整阈值消除的失败结果。

默认扩展版为在线主结果；正文 CV→最大组→CV→最小 rank 解释对同一 aggregate profile 重放。两版分列检测、组信号、rank 候选、唯一正确、错误输出、拒判及延迟，不重复跑两套训练，不读取故障标签作诊断。三个持续故障档位各一次只支持描述性结果，不能估计总体稳定准确率；弱档未过20%门限也计入全部注入分母，另外提供超过门限子集。

执行：`.venv/bin/python scripts/run_proxy_localization_suite.py --prefix fresh-`。所有 GPU 测试串行，新 run ID 保留失败与成功结果。收尾只停止自己的容器、确认时钟/显存并更新交接。
