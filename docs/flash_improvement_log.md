# FLASH 后续改进记录

状态：记录问题与复测条件，本轮不修改定位算法或阈值。用户选择继续进程内代理；物理限频、共享链路背景流量、fail-stop 均不启用。

## F01：通信定位的输出粒度不足（高优先级，已在代理测试确认）

**现象。** 对 rank0 的跨节点 size2 expert-DP AllReduce 注入 stream 等待后，rank0 与 rank8 都测得长时延。`loc-r1-comm-medium` 中分别为 16.0478 / 16.0136 ms，组内 CV=0.0010666；强档 CV=0.0005274，均低于0.1。阶段一选中实际受影响组 `[0,8]`，但阶段二没有足够差异区分两个端点。正文规则在中/强档分别输出错误 rank7/rank11；扩展版均拒绝唯一输出，不能把减少误判称为通信定位成功。

**证据。** `results/loc-r1-comm-medium/node0/profile-1.json`、`results/loc-r1-comm-strong/node0/profile-1.json`、`results/loc-r1-localization.json`。这是进程内执行迟滞代理的证据，不等同于真实网络拥塞结论。

**跨节点补充。** 用户要求只再做一轮通信后停止。`loc-r1-comm-node1-final` 对 node1 rank9 注入，实测迭代时延增加38.41%，自动检测与完整剖析通过，阶段一命中 `[1,9]`，组内 CV=0.0003198；正文和扩展均未唯一定位。两节点三轮超过20%门限的通信代理均命中目标组，均未唯一识别注入端点。另一个约4.65%弱档未触发，单列为门限覆盖问题，不能与阶段二失败混淆。本轮不再追加通信测试。

**影响。** 目前核心结果只以 `identified_ranks/candidate_ranks` 为中心，无法清楚表达“通信组已定位，但端点未判明”或“某条 rank-pair 路径异常”。共享 NIC/链路上的真实背景流量还可能同时作用于多个 rank，单一 rank 真值并非总合理。

**传播集合的实测区分。** 同一 `loc-r1-comm-medium` 只有 rank0 写入故障控制，但16个rank的迭代中位时延都增加41.94%–42.23%，详见 `results/loc-r1-communication-propagation.json`。注入控制点 `{0}`、目标 expert-DP 组 `{0,8}`、迭代层受影响集合 `{0..15}` 是三个不同对象；后者不能作为16个根因。这里的两端通信长时延也不代表完整的传播影响仅限两端。

**改进方向。** 引入组件类型与粒度（GPU/rank、通信组、逻辑 rank pair、已知网络路径），分别保存注入根因、观测受影响集合和预测组件。证据不足时明确返回通信组/路径和不可区分端点，不把所有受影响 rank 都标成根因。

**验收。** 不同节点、不同 rank 对均能正确报出目标组；单端注入若不可辨识应拒绝端点结论。真实链路实验需独立链路真值，不能任意以 rank0 代替。

## F02：“取最小通信时延 rank”缺少通信执行退化的独立验证（高优先级，方法边界）

计算晚到时，快 rank 等待较久、迟到 rank 等待较少，能够解释论文的最小值规则；网络传输执行期间变慢时，受影响端和对端都可能测得更长时延。F01 表明当前代理下不能直接沿用同一解释。

**改进方向。** 先区分计算/到达迟滞与通信执行异常，或返回可疑组件类型而非强求单 rank；考虑多窗口、方向性、跨组传播时序等证据。需要验证时，可研究低频的按需 P2P/计算验证，但这是新增模式/开销，不能混称为现有两状态 FLASH 已实现的能力。

**验收。** 同样通信执行故障语义、同样样本分别对照旧/新规则；单列检测、组命中、端点定位、错误输出与拒判；保留无法辨识的案例，不通过降低 CV 门限凑结果。

## F03：结果与真值的层级、Precision/Recall 口径需统一（高优先级，报告已部分澄清）

注入点不等于所有受影响 rank；候选集合也不等于正式输出。本轮报告已将 `identified_ranks` 用于主指标，把歧义 `candidate_ranks` 的覆盖情况单列。扩展拒判即没有正预测，该类 Precision 未定义，不能写成100%；弱档未触发仍在全部注入分母，另列实测超过20%的子集。

**改进方向。** 增加独立的通信组/逻辑链路命中指标和多组件集合指标，避免把“组命中、端点未知”完全压成一个 rank 准确率。同时记录检测事件指标，禁止把事件检测准确率当定位准确率。

**验收。** 对人为构造的单 rank、rank pair、共享链路多 rank 影响样本，各层真值与输出一一对应；错误端点、正确组但端点歧义、漏检三种结果分别可见。

## F04：启动期与共享环境自然波动的触发需要复核（中优先级，已观察、原因未确定）

此前无 padding 的 `s343-r1-profile-1-flash` 没有故障注入，却自动触发一次：变点零基 iteration12，实际触发前已完成 step50，观测退化26.77%。独立 `s343-r1-healthy` 1800步约39.385秒未触发。共享 GPU 的真实资源退化不能排除，不能仅凭未注入故障就断言算法根因错误。

**改进方向。** 记录启动稳定性和资源旁证，区分启动变化、瞬态恢复与真实外部退化。先复测不同负载与无 padding 情况，再决定是否调整启动过滤或持续性判据。本次故障矩阵250ms固定等待会平滑相对波动，不能用其负控0次证明本问题已修复。

**验收。** 固定数据、规则与运行环境，报告无注入触发的实际观察时长和全部事件；不将短测0次推广成长期0误触。

## F05：短训练的 profile 生命周期可能提前截断（中优先级，实验运行器问题）

原 `--force-profile-at` 不禁止此前自动触发，旧轮先自动剖析，后将显式触发延迟至 step1301，训练剩余时间不足。runner 在训练结束后很快停止控制器，可能没有完整的20秒训练覆盖。本次已新增 opt-in `--force-profile-only` 隔离受控开销实验，并延长故障轮，**但通用生命周期等待逻辑尚未系统修复**。

**改进方向。** 显式记录本地 profile start/stop，区分 GPU 采样截止和写盘/聚合完成；按训练仍活跃的窗口验收，有限等待控制器完成并在取消时落盘状态。

**验收。** 正常结束、训练提前退出、超时、手动取消均有明确完成/中断状态，不能把不完整采样算有效定位结果。

## F06：逐组最小值汇总会引入额外计算根因（中优先级，正文规则对照已确认）

`loc-r1-compute-node1-rank10` 的唯一计算注入点为rank10，实测时延增幅45.93%；同一profile的正文规则输出 `[10,15]`，工程扩展输出 `[10]`。说明即使是计算晚到，多个通信组的传播等待也可能让简单候选并集引入额外rank。扩展在本例去除了误报，但不能据此保证所有拓扑和多故障情形都有效。

**改进方向与验收。** 将跨组一致性、真正独立的证据来源和同步传播区分开；固定同份原始profile比较规则，并同时报告额外FP和唯一正确率。保留此额外rank15案例，后续修改不得只保留成功输出。证据：`results/loc-r1-compute-node1-rank10/node0/profile-1.json` 与同轮rank注入日志。

## F07：混合并行的组标注与累积分数需严格定义（中优先级，3.4.6复核确认）

当前按通信组成员匹配角色，不能总是唯一还原实际 communicator 的语义。`loc-r1-hybrid-compute` 的一个4成员 communicator 同时匹配 `expert_ep` 与 `attention_dp`；哈希不同也不证明物理路径或因果证据独立。玩具模型的角色数也不等同于论文2/4/4/5组，不能强行对齐。

扩展原生 `ranking.score` 是经过筛选/阈值后的证据之和，可能使用 `expert_ep` 或 `special`（例如训练控制同步）证据；它不是论文公式3-2对所有参与并行组求和的唯一还原。`hyb346-r1-ep8-tp1-pp1` 的扩展目标证据含attention-DP与expert-EP；TP2/PP1轮含expert-EP、expert-TP与special。这些证据对当前合成负载有用，但不能直接推广为生产MoE中独立稳定维度的证据。

**改进方向。** 框架侧提供 communicator 真实用途/成员/调用类别，区分训练控制通信和模型并行通信，明确EP动态组的使用策略；离线消融EP/special对定位与误报的影响。单列角色数、不同comm哈希数、按公式全组累计、筛选后扩展累计和按哈希去重累计，不用同一个“组数/得分”名称混算。

**验收。** 同成员不同用途、同comm多角色、单例DP、PP分阶段场景均有正确标注；多个标签不会被误算为多份独立证据。3.4.6本轮只做单次拓扑覆盖，重复样本不足时不制造标准差、不要求累计分单调增长。详见 `results/hyb346-r1-hybrid-346.json`。

## 与 GreyHound 比较的证据边界

GreyHound 论文 §4.3 的设计是先筛可疑组，暂停训练后分解 ring/tree 为 P2P 测试，目标是慢 GPU 或拥塞逻辑链路；它比只看集合通信的最小 rank 多了一层主动验证。当前 checkout 的 `global_controller.py:172–218` 实际执行环验证，树验证调用被注释；任务与结果保留发送/接收 rank 映射，`mitigation_plan.py:50–75` 又将其聚合为 communicator 最大时延，`find_slow_reason` 返回 comp/comm。没有发现可直接复用的、完善的物理 NIC/端口根因输出。因此应借鉴验证机制与组件粒度，不能声称当前 GreyHound 代码已经提供了严谨的端点/NIC 精度基准。

GreyHound 论文表3/4的检测准确率/FPR/FNR是事件级指标，不能等同于链路/端点定位 Precision/Recall；中文论文图3-9也没有按计算和通信拆分结果。尚未在本轮同负载实测 GreyHound，不能依据阅读就宣布两者实测优劣。
