# FLASH 第三章工程复现要求

本文把《中文论文》第三章（3.1–3.4，PDF 第 35–61 页附近）的 FLASH 方案整理为实现规格，并完整列出 3.4 的实验矩阵。参数按论文原文记录；原文没有给出精确定义或存在冲突的地方列在末尾，复现时不应自行补成确定事实。

## 1. 系统目标和范围

FLASH（Fast Low-overhead Automatic Straggler Handling）用于分布式训练期间的性能退化（fail-slow）定位和停机故障（fail-stop）检测。其预期能力是：通过 NCCL API 劫持采集通信数据，在训练常态以低开销监控；发现持续迭代性能退化后短时进入剖析模式；定位到慢 rank，并映射到节点。MoE 场景主要利用 DP、TP、PP 等相对稳定的通信组及其交叉证据，不把动态 EP All-to-All 本身作为主要诊断依据。

论文描述的控制状态只有两个：监控 `0`、剖析 `1`。框架训练代码无需改动主逻辑；框架侧少量回调提供迭代时间和并行组成员信息。数据平面由训练进程内的 C++ NCCL Probe 实现，节点本地控制器用 Python 读取共享内存，全局控制器通过 Redis 协调节点并作定位决策。

## 2. FLASH 的数据流和部署要求

### 2.1 监控数据

- 训练框架在每个迭代结束时上报迭代时间。Redis 列表键为 `iter_time_{rank}`，元素格式为 `iteration:time_ms`；全局性能退化检测以 Rank 0 的迭代时间为基准。
- 迭代时间历史默认最多保留 500 条。论文报告每次 Redis 上报约 100 微秒。
- `libncclprobe.so` 在监控模式记录 NCCL 调用时间戳和调用元数据，不启用 CUDA Event。节点本地控制器从共享内存读取事件间隔，用于停机故障检测。
- 训练初始化时还需向 Redis 上报 parallel states，包括 TP、DP、PP、EP 等组成员信息，供通信组分类和交叉定位使用。

### 2.2 剖析数据

- 全局控制器把 Redis 控制状态置为 `1`。各节点控制器以 100–500 ms 周期轮询状态，发现变化后将状态写入本地共享内存中的原子变量。
- Probe 在 NCCL Group 结束等检查点读取本地状态。剖析模式启用 CUDA Event；监控模式只记时间戳。
- 本地控制器按 communicator 汇总 `min/max/avg/std` 并上报 Redis；全局控制器读取剖析统计和 communicator 拓扑，执行两阶段定位，再将状态恢复为 `0`。
- 剖析持续时间按 `profile_period = max(latest_iter_time × 2.2, 20.0)` 计算。单位应统一为秒；论文称该窗口约覆盖 2.2 个迭代且至少 20 秒。实验文字另称典型持续 20–50 秒。

### 2.3 NCCL Probe 与共享内存

- 用 `LD_PRELOAD` 导出与 NCCL API 同名的包装函数，通过动态链接器解析原始函数；记录事件/必要时插入 CUDA Event 后调用原函数并返回原结果。
- 采用惰性初始化：第一次 NCCL 调用时初始化全局单例状态、句柄、CUDA Event 和 communicator 元数据。
- 通信组简化模式至少记录 communicator 地址、`id_hash` 和全局 rank；按 `id_hash` 将 communicator 归为同一通信组。完整格式可包含 ring/tree 信息；不可用时降级至简化格式。
- 节点内使用共享内存环形缓冲区。元数据区包含字段数、最大记录数、当前记录数、头尾指针、初始化魔数、全局事件计数器和控制状态；事件记录包括 communicator 地址、调用序号、数据量、duration、组标识等字段。
- 论文给出的 Probe 写入路径在尾部加锁写入、更新指针/计数后解锁，约 50–200 ns。Python 读取侧无锁，读取记录后清空缓冲区并重置计数。论文报告写入约 1000 次/秒/进程、读取约 0.2 次/秒。
- 剖析时按 NCCL Group 复用计时：每个 Group 仅记录一次开始和结束 CUDA Event，将 Group 总耗时写入该 Group 的记录。结束事件在 Group 结束处记录并同步，再以 `cudaEventElapsedTime` 计算时长。论文说明该计时覆盖 GPU kernel 内同步等待（包括 NCCL `waitPeer()` 等待）。

### 2.4 部署接口

- 安装 Python 包 `robust_training_flash`（含控制平面和编译好的 NCCL Probe）。
- 启用框架迭代时间上报的环境变量：`FAILSLOW_AWARE=TRUE`。
- 启动训练进程前设置 `LD_PRELOAD` 指向 Probe 共享库。
- 默认配置文件：`~/.robust_training_flash/config.json`，包括 Redis 连接、检测阈值和剖析时长；首次运行自动生成默认配置。
- 论文称框架改动少于 10 行，范围包括迭代时间回调和并行状态上报。Megatron-LM 示例为 `logger.py` 约 5 行、`training.py` 约 3 行、parallel states 上报约 2 行。

## 3. 监控和故障判据

### 3.1 BOCD 变点检测

- 输入：Rank 0 迭代时间序列。训练前 3 个迭代跳过；默认以 30 个迭代为滑动窗口；BOCD 前剔除 `z-score > 3.0` 的点。
- 论文称使用 Rbeast 库实现 BOCD。运行长度后验 `P(r_t | x_{1:t})` 中，`P(r_t=0 | x_{1:t})` 超过 `thresh_prob = 0.8` 时形成候选变点。
- `degradation_thresh = 0.2`：性能下降超过 20% 才进入后续处理。
- 若相邻变点间距小于 2 个迭代，只保留首个变点，过滤后续重复点。

### 3.2 持续性过滤

对候选变点定义：`x_l` 为变点左侧数据，`x_r` 为包含变点的右侧数据，`x'_r` 为去掉右侧第一个点后的数据。计算：

```text
baseline_mean = mean(x_l)
degraded_mean = mean(x_r)
recent_mean = mean(x'_r)
recovery_ratio = (degraded_mean - recent_mean) / (degraded_mean - baseline_mean)
```

当 `recovery_ratio >= 0.75` 时，论文将其视为恢复超过 75% 的瞬时波动并过滤；小于 0.75 时视为持续退化，进入剖析。论文举例：17345、26932、19323 ms 对应约 0.79，判为瞬时；若 `recent_mean=25000 ms`，比率约 0.20，判为持续。

### 3.3 Fail-stop 检测

本地控制器统计每个 rank 在动态时间窗内的 NCCL 调用。若窗口内没有新调用，判为 fail-stop，写入 Redis 的 `failstop_ranks` 列表并由全局控制器汇总告警。窗口按迭代时间动态设置，论文举例为 `2 × iteration_time`；未给出比该示例更具体的固定值。预期检测延迟约等于窗口长度。

## 4. 剖析和两阶段慢 rank 定位算法

### 4.1 通信组构建和标签

1. 从 communicator 获取 `id_hash` 和全局 rank，按 `id_hash` 聚合成通信组。
2. 结合 parallel states 将组映射为 TP、DP、PP stage、`expert_dp`、`expert_tp` 等标签；无法映射时作为特殊组。
3. 忽略单 rank 通信组。

### 4.2 阶段一：通信组筛选

对每个标签计算各通信组的 `max_avg_latency`（组内 communicator 平均时延的最大值）。若该标签只有一个组，按论文实现直接进入 rank 分析；多个组时，先计算这些组 `max_avg_latency` 的 CV（`std/mean`）。若 `CV < 0.1`，跳过该标签的通信组筛选；否则取 `max_avg_latency` 最大的组作为候选组。论文方案解释为慢 rank 会拖长同步通信组的整体时延。

论文 3.4.4 的组级实验另用归一化得分展示候选信号：

```text
score_clique = (t_clique - μ_cliques) / μ_cliques
```

其中 `t_clique` 是该组平均通信延迟，`μ_cliques` 是同类型组的平均延迟。该得分是实验分析指标，论文没有把它定义为控制器实际筛组选组的替代规则。

### 4.3 阶段二：rank 筛选

在候选通信组内，按 rank 汇总其参与的 communicator 时延并计算 `avg_latency`。若 rank 平均时延的 CV `< 0.1`，跳过该组；否则平均时延最小的 rank 是慢 rank 候选。直觉依据是集合通信同步等待：快 rank 到达同步点后等待慢 rank，CUDA Event 会把等待计入；慢 rank 较晚到达、等待较少，因此可能测得更短时延。

论文另提到“默认 20% 百分比阈值筛选离群值”，但没有给出该阈值的精确公式、比较方向或它与“取最小平均时延 rank”的组合次序。实现时需核对原始代码/配置，不能仅凭章节文本补出公式。

rank 级实验展示的归一化得分为：

```text
score_rank = (μ_clique - t_rank) / μ_clique
```

其中 `μ_clique` 是组内 rank 平均延迟，`t_rank` 是待评估 rank 的平均延迟。正值代表低于组平均时延、因而更可疑。这也是 3.4.4 的实验度量，不应取代 CV 和候选 rank 规则。

### 4.4 混合并行证据

对 rank 参与的多个并行标签分别定位并输出证据；多个标签一致指向同一 rank 时，置信度提高。论文示例是将 `ppstage0_dp` 与 `expert_dp` 两组都指向 rank 4。累积得分在 3.4.6 中定义为故障 rank 所参与并行组得分之和。

### 5.3 GREYHOUND 与 FLASH 的边界

3.4.4 中 GreyHound 只作为定位准确率对比基线，原文将其描述为使用 ACF 迭代计时和 stop-the-world 定位。它的三阶段微基准属于对比对象的实验/机制，不能写成 FLASH 的状态机、剖析流程或定位算法。FLASH 本章方案是两状态控制（监控/剖析）和两阶段定位（通信组筛选/rank 筛选）。

## 6. 原文歧义和复现前需核对项

1. **持续性条件互有冲突。** 3.2.2 给出 `recovery_ratio`、相邻变点距离 `<2`、跳过前 3 迭代、z-score `>3.0` 四项；3.4.3 又称剖析触发需“持续超过 20 个迭代”。3.4.5 则说明右侧保护区通常仅 `k=1–2`，对应 1–2 个迭代后识别。不能从文本判断“超过 20 个迭代”是独立持久性条件、误写还是另一实现版本，需检查代码/配置。
2. **性能下降 20% 的分母由复现实现作出明确选择。** 论文给出 `degradation_thresh=0.2`，但没有说明百分比的分母。当前 `flash/detection.py` 按迭代耗时计算 `(degraded_mean - baseline_mean) / baseline_mean`，即相对变点前平均迭代时间的时延增幅；这样“20% 退化”有固定的前态基准，且 5% 注入应被阈值拒绝。此分母是工程解释，不是论文原文给定的公式。
3. **rank 的 20% 百分比阈值不完整。** 没有公式、比较方向或与“取最小 avg_latency rank”规则的组合次序；正文也未说明条件不满足时是拒绝整个组还是只不报该 rank。
4. **剖析时长/覆盖窗口口径。** `max(latest_iter_time×2.2,20秒)` 的单位转换未展开；算法描述说约 2.2 个迭代，定位时延评估又说至少一个完整迭代。配置实现需统一迭代时间单位和结束条件。
5. **CV 描述有层级差异。** 3.2.3 强调候选通信组内 rank 时延 CV；3.3.2 明确同时做“多个组的 max_avg_latency CV”和“rank avg_latency CV”。复现应按 3.3.2 实现描述实现两处检查，并以原始实现确认。
6. **Redis 上报和采样细节不完整。** 未给出所有键名、统计值序列化格式、过期/清理策略、共享内存容量、溢出处理和事件丢失恢复方式；`failstop_ranks` 是唯一明确列出的故障列表键。
7. **实验数值存在汇总口径差异。** 端到端开销报告为约 0.05%，无误触部分又称正常开销 `<0.01%`；表中硬件称 H200 140 GB，正文另处称 141 GB；框架改动分项约 5+3+2 行而总述为小于 10 行。这些都应保留为论文报告值/口径差异，不据此改写参数。
